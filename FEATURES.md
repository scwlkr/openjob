# Features

## Authenticated personal workspace

`/workspace` uses the existing Firebase session and `/api/v1/workspace` for owner-private Tasks and an OpenJob Personal Calendar. The existing Group app links to it from the User menu. Create, edit, schedule, complete, unschedule and delete personal Tasks; linked Calendar changes stay atomic. The Firestore REST adapter stores one validated owner document with compare-and-set and active-user/deletion fences; the current bounded record limit is 900 KB. Account deletion removes the private workspace before finalizing identity deletion. Existing `openjob workspace snapshot` and `openjob workspace command --input FILE|-` use the same authenticated API. No fixture identity header selects an owner.

The Mail tab explicitly enables three invented mailboxes and six messages in the same owner-private document. Search/read, create a linked private Task, schedule/complete it and save/edit a reply through the shared API/CLI. Drafts and local Simulated Sent persist; activation preserves existing state. Mail agents have seven available scopes across five named resources, including separate read, draft and simulated-send rights on specific example mailboxes. Actual sending always denies. Personal Tasks share status/title/planned-UTC-day filters with `openjob workspace tasks`; midnight overlap is explicit and unscheduled work is excluded only when a planned day is selected. Existing scoped snapshots retain redaction and revocation. Calendar navigation clears hiding Task filters while preserving edits. Calendar blocks offer Open linked task only for an exact visible owner/calendar/event/Task relationship; it focuses the Task for editing, completion or source-Mail access. Unsaved Task titles, new-task text, schedule fields and Calendar editor state survive tab navigation and clear on identity changes. Private Tasks expose Open source mail only for the exact visible owner/account/message pair; it selects that mailbox and Inbox, clears hiding filters and focuses the reader. Unsaved replies stay per message, and composition/editor text survives navigation. Provider preview stays separate and read-only; Group Tasks receive no mailbox references.

Mail in this entrypoint uses a visibly synthetic, owner-isolated provider read adapter behind the authenticated API and CLI. Stable account-qualified references, message pagination and explicit sync/capability states prepare the connector boundary. The UI selects accounts and reads provider example Calendars separately from the saved OpenJob Calendar; example-to-Task saves only its title, never a provider mailbox link. Personal agents use separate hashed opaque credentials with explicit Mail/Task/Calendar scopes and resources, 24-hour expiry, stable audit IDs and revocation fenced through the same durable document. Existing CLI issues a private 0600 token file; the app lists effective access and revokes grants without displaying secrets. Group read-only grants do not authorize personal data. Signed synthetic identity/fake Firestore tests verify the adapter and HTTP clients. No live database/auth/provider integration or deployment was exercised. A separate Gmail REST message/label read adapter is implemented with a closed execution gate and invented HTTP proof. An owner-bound connection reader and private credential-broker interface now exercise that mapper through the same API/CLI/app with explicit mock accounts in the isolated HTTP harness; consent, expiry, revocation, identity changes and broker-reference changes deny reads. A separate Firestore metadata repository and injected token-vault broker support owner/revision checks, stale-write rejection and revocation over synthetic transport. No real vault is provisioned. A server-only mock OAuth lifecycle binds new-account state/PKCE/nonce and provisions invented vault data before exact-reservation approval; it is not a configured callback or real identity verifier. An optional bounded Firestore transaction adapter proves one-use state consumption across reconstructed instances, erasing PKCE material while retaining spent hashes until expiry; it remains unbound from production. Production has no configured reader/store/broker or live mode. The API/CLI/app expose its not-connected and provider-consent-required status separately from synthetic accounts; no live connection, token input or enable control exists. See [the personal workspace guide](docs/PERSONAL_WORKSPACE.md).

## Integrated workspace prototype

`npm run dev:workspace` opens `/workspace`: simulated Gmail/Outlook/IMAP Mail, Calendar, personal Tasks and scoped agent controls backed by one persistent local HTTP service and shared domain/CLI. Read/compose/save drafts, turn mail into a private Task, schedule/complete work, edit/delete calendar blocks, inspect resource-limited agent access and revoke it. Mail has Inbox, Drafts and Simulated Sent folders with mailbox-aware counts and case-insensitive subject/people/body search. Calendar has Agenda/Day/Week views, UTC date navigation and calendar filtering; edits retain their original calendar. Scoped simulated agents can attempt actual personal Task creation through the shared API, with visible allowed/denied results and immediate revocation. Personal Tasks support title edits, schedule editing, unscheduling and confirmed deletion; linked Calendar blocks stay consistent and source Mail stays intact. The one-command --fresh launcher seeds an isolated demo without credentials and preserves existing saved work. Owner views are isolated. Real sending is always disabled. Saved drafts can be reopened/edited without changing their mailbox; explicit Simulate send moves them into local Simulated Sent. Agents need a separate simulation capability as well as draft access; this cannot enable actual delivery. This is fixture-only application behavior; provider OAuth/sync and new production authentication are not implemented. The authenticated native personal workspace uses this same API; its Mail remains invented and online-only. See [the demo walkthrough](docs/WORKSPACE_DEMO.md).

## Task scheduling slots

CLI tables preserve optional fields found in later rows, including scheduled slots and due dates, with blank cells for missing values. JSON/JSONL shapes remain unchanged.

The shared Task API and CLI accept an optional planned work interval independently of the date-only due date. Explicit time zones normalize to UTC; both endpoints are required, end follows start, and clearing the slot preserves the Task and due date. Existing membership and completed-Task rules apply. This stores an OpenJob plan; it does not create provider calendar events. The web editor creates, edits and clears slots with explicit UTC inputs; Task cards show the interval in UTC, including an accessible description. Validation, network failure and authentication recovery preserve the entered interval. Native visual scheduling controls remain unimplemented.

## Scoped agent Task reads

A signed-in human can issue, list and revoke a named agent grant through `/api/v1/agent-grants`. Each opaque credential permits only Task list/item GETs in one current Task Group for 24 hours. The service stores its hash, binds it to the owner's membership generation, and rechecks access before returning data or a conditional 304. Revocation, expiry, account deletion and membership loss/rejoin stop access. Grants cannot modify Tasks, administer Groups, read other APIs, Mail or Calendar. Account deletion removes owned grant records. Owner management UI and broader scopes remain future Linear work.

Human CLI `agent grant` issues the existing fixed-scope grant to a new private mode-0600 token file; only public metadata is printed. Explicit Group/name/path are required, overwrite and stdout token delivery are rejected, and failed delivery identifies the grant for revocation. Issuance does not retry transient/ambiguous failures. `agent list` and confirmed `agent revoke` use the same human profile and owner-only API.

The existing CLI accepts an explicit `--agent-token-file <path|->` on `task list` and `task show`, together with explicit `--group`. It never refreshes or falls back to human credentials for these reads. Isolated API/Firestore/CLI fixtures verify behavior; no production grant is created by development checks.

### Native personal workspace

The signed-in Expo app opens personal Mail, Tasks, Calendar and Agents while retaining Existing Groups. Opt in to invented mailboxes, read/search/mark messages, create private Tasks, edit/complete/schedule/unschedule/delete them, and open their exact Calendar/source Mail links. Compose/edit reply drafts and simulate sending; actual delivery remains disabled. Review effective agent permissions/activity and confirm revocation; issuance stays in the existing CLI. Unsaved editors survive module/Group navigation and clear on identity changes. Existing Firebase sessions authenticate every operation; no token entry or personal disk cache. Offline edits/sync, live providers and device acceptance remain unimplemented or unverified. See [the personal workspace guide](docs/PERSONAL_WORKSPACE.md).
